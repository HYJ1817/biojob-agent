# BioJob Agent 详细设计文档

- 文档状态：已由用户批准，可进入阶段 0 实施计划
- 设计日期：2026-08-11
- 目标平台：Windows 桌面端，单用户、本地优先
- 产品定位：面向生物工程本科应届生的秋招岗位发现、匹配、简历定制与投递管理 Agent
- 技术底座：Hermes Agent 分支，保留其通用 Agent、模型、Skills、会话和定时任务能力

## 1. 背景与问题

目标用户为烟台大学生物工程专业 2027 届本科生，正在准备 2026 年秋招。优先方向为制药生产/工艺、生物工艺、发酵、QA、QC、GMP、细胞培养和实验技术；不重点考虑要求硕士/博士的高门槛研发、药物合成、临床项目管理和医药销售。

当前已有一份不完善的基础简历，但没有成熟的投递表，也没有正式实习或项目经历。求职过程中最耗时、最容易失控的部分不是单次问答，而是以下连续流程：

1. 持续发现符合学历、专业和方向的新增岗位。
2. 去除重复、失效和明显不匹配的岗位。
3. 判断是否值得投递，并给出可追溯的判断依据。
4. 针对确定要投递的岗位调整简历，同时禁止虚构经历。
5. 保存岗位链接、简历版本、投递状态和后续跟进动作。
6. 长期复盘不同方向、地区和企业类型的投递效果。

BioJob Agent 的核心不是通用聊天，而是以结构化投递数据为中心，把上述流程连接起来。

## 2. 已确认的产品决策

1. 最终形态为独立 Windows GUI，而不是仅在 Codex 对话中运行。
2. 采用“自动发现候选岗位 + 用户确认后进入正式投递表”的混合模式。
3. 以重点药企为核心，同时通过稳定接口和公开搜索发现其他相似企业。
4. SQLite 是唯一事实数据源；Excel 是方便查看、筛选、跳转和手工补充的导出视图。
5. 岗位进入“准备投递”状态后才生成定制简历，避免产生大量无用版本。
6. Excel 必须包含可点击的职位详情、申请页面、企业招聘主页和本地简历链接。
7. Hermes Agent 是唯一主底座；FindJobs-Agent 和 resume-tailor-plugin 提供求职领域能力参考或可移植模块；OpenCode 和 OpenMinis 只作为架构参考。
8. 第一版不做自动登录、自动打招呼、自动提交申请，也不绕过验证码或平台风控。
9. 第一版主要服务本人，不提供账号系统、云同步、多人协作或公开 SaaS。

## 3. 产品目标与非目标

### 3.1 目标

- 每天用较少时间完成“发现—确认—分析—准备—记录—跟进”的闭环。
- 提高生物工程本科岗位的有效覆盖率，而不是追求无差别岗位数量。
- 对每个推荐结论提供 JD 原文证据，避免只给一个不可解释的分数。
- 形成稳定、可备份、可导出的投递数据库。
- 允许切换不同模型服务商和自定义兼容 API，不把产品绑定到单一模型。
- 所有简历内容可追溯到个人事实主档案，防止 AI 编造。
- 通用 Agent 底层与求职业务解耦，便于吸收 Hermes 上游更新。

### 3.2 非目标

- 不构建与 Hermes、OpenCode 同等规模的通用 Agent 平台。
- 不保证覆盖所有招聘网站或所有企业。
- 不自动替用户提交申请、发送消息或回答招聘方问题。
- 不将 LLM 评分视为招聘结果预测。
- 不根据不存在的经历补齐 JD 缺口。
- 不在第一版实现移动端、浏览器扩展、云端账户和团队招聘功能。
- 不在第一版做复杂的面试模拟、邮件自动回复或人脉拓展。

## 4. 设计原则

1. **人工确认优先**：候选发现可以自动化，投递和简历事实变更必须由用户确认。
2. **事实与生成分离**：个人主档案只保存事实；岗位简历是事实的选择、排序和表述变体。
3. **本地数据优先**：简历、画像、岗位库和密钥默认只保存在本机。
4. **确定性规则先于 LLM**：学历、毕业年份、岗位方向等硬条件先由规则判断，LLM 负责语义理解和解释。
5. **可追溯**：岗位来源、原始 JD、评分版本、简历版本和用户决策都有记录。
6. **渐进式自动化**：先稳定完成岗位表和简历闭环，再增加更广的数据源和辅助功能。
7. **上游友好**：尽量不侵入修改 Hermes 核心，通过领域包、API 和独立 UI 功能区扩展。

Hermes 的通用持久记忆可以记录交互偏好和工作习惯，但不能新增、修改或覆盖个人事实主档案。发生冲突时，以用户明确确认的结构化事实为唯一依据。

## 5. 总体架构

```text
BioJob Desktop（Electron + React）
        │
        │ Hermes 现有 JSON-RPC/WebSocket + BioJob HTTP/事件接口
        ▼
Hermes Runtime
├─ 会话、Skills、记忆、权限和工具调用
├─ 多模型 Provider、流式输出和模型选择
├─ 定时任务与后台运行
└─ BioJob Domain Service
   ├─ 个人事实主档案
   ├─ 岗位来源适配器
   ├─ 规范化、去重和失效检查
   ├─ 生物医药岗位匹配
   ├─ 投递状态机
   ├─ 简历定制与版本管理
   └─ Excel 导出
        │
        ▼
SQLite + 本地文档目录 + Windows Credential Manager
```

### 5.1 主底座策略

项目从 Hermes Agent 的固定上游提交创建分支。实现阶段必须在仓库中记录上游仓库地址、固定提交 SHA、同步日期和本地修改范围。Hermes 的 Provider、Agent 循环、Skills、会话、权限、后台任务和桌面打包能力原则上保持原样。

求职领域代码放在独立边界内：

- 后端领域包：`biojob/`
- 桌面功能区：`apps/desktop/src/features/biojob/`
- 求职 Skills：`skills/biojob-*/`
- 数据源插件：`biojob/sources/`
- 数据迁移：`biojob/migrations/`

只有导航注册、应用名称/图标、后台启动和领域 API 暴露需要触及 Hermes 公共接缝。不得把岗位规则散落在通用 Agent 或 Provider 代码中。

### 5.2 运行时边界

BioJob 业务代码只依赖一个统一的 `AgentRuntime` 接口，接口提供：

- 结构化文本生成
- 流式进度
- 工具调用
- 模型能力查询
- 任务取消
- 会话与审计标识

第一版只实现 `HermesRuntimeAdapter`。OpenCode 可在后续通过独立适配器接入，但不属于第一版依赖。

## 7. 核心用户流程

### 7.1 首次使用

1. 用户导入现有 Word 或 PDF 简历。
2. Agent 提取教育、技能、实验经历和求职偏好，形成“个人事实主档案草稿”。
3. 用户逐项确认、修改或标记“尚未确认”。
4. 系统为每条事实分配稳定 ID，并记录来源文件和确认时间。
5. 用户配置至少一个模型 Provider，并进行连接测试。
6. 用户启用默认生物医药岗位方向、重点企业和地区偏好。
7. 系统创建 SQLite 数据库、文档目录和第一份空白 Excel 投递表。

未经用户确认的简历推断不得进入可用于生成简历的事实集合。

### 7.2 每日岗位发现

1. 定时任务读取启用的数据源、关键词和上次增量游标。
2. 数据源适配器获取原始岗位并保存原始快照。
3. 系统规范化公司、岗位名称、城市、时间、学历、专业、JD 和链接。
4. 去重器合并重复来源，但保留每个来源链接。
5. 硬规则排除明显不符合要求的岗位。
6. 匹配引擎对剩余岗位生成分数、证据、优势和差距。
7. 岗位进入“待确认候选池”，而不是直接进入正式投递表。
8. GUI 和系统通知显示当日新增数量、较高匹配岗位和失败数据源。

### 7.3 候选确认

用户可以对候选岗位执行：

- 保留：进入正式投递表，初始状态为“待决定”。
- 忽略：记录忽略原因，防止后续重复推荐同一岗位。
- 稍后处理：继续留在候选池。
- 错误反馈：标记解析、分类或去重错误，用于修正规则。

批量保留和批量忽略必须在提交前显示影响数量。

### 7.4 准备投递

1. 用户将岗位状态改为“准备投递”。
2. 系统检查原始链接是否仍有效，并提示截止时间。
3. Agent 读取 JD、个人事实主档案和基础简历。
4. 系统生成匹配报告和建议修改清单，不立即覆盖任何文件。
5. 用户确认修改策略后，生成独立的 Word 简历；可选生成 PDF。
6. 新简历保存为版本化文件，并回写到岗位记录和 Excel 超链接。
7. 用户点击“立即申请”跳转到申请页面，自行完成投递。
8. 用户将状态更新为“已投递”，系统记录时间和后续跟进日期。

### 7.5 跟进与复盘

系统每天列出：

- 临近截止但尚未决定的岗位
- 已准备简历但尚未投递的岗位
- 到达跟进日期的已投递岗位
- 链接失效或岗位关闭的记录
- 新收到的笔试、面试、拒绝和 Offer 状态

复盘统计只描述事实，例如各方向投递数、回复数和进入面试数，不声称存在因果关系。

## 8. 功能模块

### 8.1 首页仪表盘

首页回答“今天应该做什么”，显示：

- 今日新发现、待确认、高匹配候选数量
- 准备投递、已过截止、需要跟进数量
- 最近七天投递状态变化
- 数据源健康情况和上次搜索时间
- 快捷动作：开始搜岗、导入岗位链接、确认候选、导出 Excel

### 8.2 候选岗位池

支持按岗位方向、地区、企业类型、匹配分数、数据源和发布日期筛选。列表必须显示公司、岗位、城市、方向、匹配分数、关键理由、截止时间和“查看 JD”链接。

### 8.3 正式投递看板

默认状态：

```text
待决定 → 准备投递 → 已投递 → 笔试 → 面试 → Offer
              └──────────────→ 拒绝
待决定/准备投递 ─────────────→ 放弃
任意未完成状态 ──────────────→ 已失效
```

状态变更记录操作者、时间、旧状态、新状态和备注。系统不自动把岗位标为已投递。

### 8.4 岗位详情

岗位详情包括：

- 原始 JD 和规范化字段
- 所有来源与可点击链接
- 发布、截止、抓取和最近检查时间
- 匹配总分及每个维度的证据
- 明确优势、可弥补差距和硬性缺口
- 用户决策、状态历史和备注
- 关联的简历版本、匹配报告和投递记录

### 8.5 简历中心

简历中心包含：

- 个人事实主档案
- 原始基础简历
- 事实确认队列
- 按生产工艺、QA/QC、细胞培养等方向生成的基础变体
- 每个岗位的定制版本
- 修改差异、生成模型、提示模板版本和生成时间

任何事实修改都必须先更新事实主档案，再生成新的简历版本；不得直接把模型生成内容反向当作事实。

### 8.6 Agent 对话

对话用于调用产品能力，而不是替代结构化页面。支持的典型指令包括：

- “搜索今天新增的 QA、QC 和生物工艺岗位。”
- “保留候选 2、4、7，忽略其他岗位。”
- “这个岗位为什么只有 63 分？”
- “把荣昌生物这个岗位改为准备投递。”
- “根据这个 JD 给出简历修改方案。”
- “导出最新投递表。”
- “今天有哪些岗位需要跟进？”

涉及状态改变、生成文件、覆盖导出或批量操作时，必须显示结构化确认。

### 8.7 Provider 设置

设置页复用 Hermes Provider 能力，至少支持：

- OpenAI 兼容 Chat Completions
- OpenAI Responses API
- Anthropic Messages API
- Google Gemini
- OpenRouter
- Ollama 或其他自定义本地端点

每个 Provider 可配置显示名称、Base URL、凭据、默认模型、超时和能力标记。用户可以为岗位粗筛、深度匹配和简历生成选择不同模型，但默认只配置一个模型即可完成全部流程。

## 9. 岗位数据源设计

### 9.1 数据源优先级

1. 企业官方公开 API 或公开 JSON
2. 企业使用的公开 ATS 接口
3. 企业官方招聘网页
4. 无需登录的公开招聘聚合页或搜索发现接口
5. 用户手动粘贴的岗位 URL 或 JD

第一版不接入需要自动登录、验证码、批量打招呼或规避反爬检测的平台。

### 9.2 数据源适配器接口

每个适配器只负责一种来源，必须实现：

- `source_metadata()`：来源名称、类型、合规说明和健康状态
- `discover(cursor, filters)`：按增量游标发现岗位
- `fetch_detail(external_id)`：获取完整 JD
- `normalize(raw_record)`：转换为统一岗位结构
- `check_active(job)`：检查链接和岗位有效性
- `rate_limit_policy()`：声明访问频率和重试限制

适配器失败不能阻塞其他来源。每次运行记录成功数、失败数、耗时、HTTP 状态和下次重试时间，但日志不得保存 API Key、Cookie 或个人简历内容。

### 9.3 首批目标范围

优先覆盖齐鲁制药、鲁南制药、恒瑞医药、荣昌生物、绿叶制药、华熙生物、药明康德、康龙化成和凯莱英的官方招聘入口；实施时按照接口稳定性选择至少五家进入首发版本。另提供一个公开搜索发现来源和一个手动 URL 导入来源。

目标关键词包括：

- 生物制药、制药生产、生产技术员
- 工艺工程师、生物工艺工程师、发酵工程师
- QA、QC、质量管理、GMP
- 细胞培养、实验员、生物分析、研发助理

### 9.4 去重策略

去重分三层：

1. 精确键：来源 ID、规范化 URL 或企业岗位编号相同。
2. 业务键：规范化公司 + 岗位名称 + 城市 + 招聘批次相同。
3. 语义候选：文本相似度较高时提示可能重复，由用户确认。

合并时保留全部来源、最完整 JD、最早发现时间和最近有效检查时间。用户的投递状态和备注永远优先，不因重新抓取而覆盖。

## 10. 岗位匹配设计

### 10.1 硬规则

以下条件由确定性规则优先处理：

- 明确要求硕士或博士且不接受本科
- 明确要求已有多年全职经验
- 招聘对象与 2027 届不符
- 岗位属于销售、临床项目管理或化学合成等排除方向
- 截止日期已过或页面明确关闭

“硕士优先”“有经验优先”不能自动判为不符合，只能作为竞争风险提示。

### 10.2 软匹配评分

总分为 100 分：

| 维度 | 权重 | 说明 |
|---|---:|---|
| 岗位方向 | 25 | 与生产工艺、QA/QC、发酵、细胞培养等目标方向的相关性 |
| 学历与专业 | 20 | 本科可投、生物工程或相关专业匹配情况 |
| 实验与技术技能 | 25 | 细胞培养、CCK-8、电泳、转膜、微生物、发酵等证据 |
| 应届与经验要求 | 10 | 是否接受无正式实习或项目经历的应届生 |
| 地区与企业偏好 | 10 | 山东及周边优先，同时接受大城市 |
| 发展与岗位质量 | 10 | 培训、工艺成长路径、岗位稳定性和职责清晰度 |

每个维度必须输出：分数、JD 证据、个人事实证据、缺口和置信度。没有证据时必须写“未在 JD 中找到”，不能自行补全。

推荐等级：

- 80–100：优先确认
- 65–79：建议确认，需关注明确差距
- 50–64：谨慎考虑
- 0–49：通常忽略，但保留用户覆盖权

评分只用于排序，不替用户做最终决定。

## 11. 简历定制设计

### 11.1 个人事实主档案

主档案按事实 ID 保存：

- 教育背景和毕业时间
- 课程和成绩信息（只有用户确认后使用）
- 实验操作、对象、方法和结果
- 软件、编程和数据处理能力
- 证书、奖项、学生工作和其他经历
- 求职偏好和禁止表述

每条事实包含来源、确认状态、确认时间和可见范围。未确认、推断或相互矛盾的事实不得进入正式简历。

### 11.2 定制流程

1. 对 JD 生成需求清单和关键词清单。
2. 逐项映射事实 ID，区分匹配、部分匹配和缺失。
3. 先展示修改方案和仍无法满足的缺口。
4. 用户确认后生成 Markdown 中间稿。
5. 运行事实一致性检查和关键词堆砌检查。
6. 基于固定 Word 模板生成 `.docx`；需要时再生成 PDF。
7. 保存版本、差异和关联岗位。

禁止行为：

- 编造实习、项目、论文、实验结果或量化数字
- 把“了解”提升为“熟练掌握”
- 把课程实验包装成企业项目而不说明性质
- 仅为了 ATS 重复堆砌关键词
- 覆盖原始简历文件

## 12. 数据模型

SQLite 使用迁移管理，启用外键和事务。核心表如下：

| 表 | 作用 |
|---|---|
| `profile_facts` | 个人事实、来源、确认状态和可见范围 |
| `profile_documents` | 原始简历和其他证明文档元数据 |
| `companies` | 规范化企业、别名、地区和类型 |
| `sources` | 岗位来源配置和健康状态 |
| `source_runs` | 每次搜索运行、游标、结果和错误摘要 |
| `jobs` | 规范化岗位主记录 |
| `job_sources` | 一个岗位对应的多个来源和跳转链接 |
| `job_snapshots` | 原始 JD 快照和变更记录 |
| `job_matches` | 匹配结果、模型、规则版本和证据 |
| `candidate_decisions` | 保留、忽略、稍后和错误反馈 |
| `applications` | 正式投递状态、时间、跟进和结果 |
| `application_events` | 状态变更审计日志 |
| `resume_versions` | 简历文件、事实集合、模板和关联岗位 |
| `scheduled_tasks` | 搜索和失效检查的调度配置 |
| `audit_log` | 高风险操作和用户确认记录 |

API Key、OAuth Token 和 Cookie 不进入 SQLite；它们由 Hermes 的安全凭据层和 Windows Credential Manager 保存。

## 13. Excel 投递表设计

系统生成 `2026秋招投递表.xlsx`，SQLite 始终是主数据源。MVP 中 Excel 是只出不进的导出视图：用户应在 GUI 中修改状态、备注和标签，然后重新导出。系统不会读取用户手工修改过的 Excel，避免覆盖冲突和公式安全问题。Excel 受控回导属于明确延期功能。

工作簿包含：

1. `投递总表`：用户确认保留的正式岗位。
2. `候选岗位`：尚未确认的候选岗位。
3. `本周行动`：需要确认、投递、截止或跟进的记录。
4. `数据字典`：状态、评分和字段含义。

`投递总表` 主要列：

- 公司
- 岗位名称
- 岗位方向
- 城市
- 企业类型
- 招聘类型
- 学历要求
- 专业要求
- 匹配分数
- 推荐等级
- 核心优势
- 主要差距
- 发布日期
- 截止日期
- 当前状态
- 投递日期
- 下次跟进日期
- 来源
- 查看 JD
- 立即申请
- 企业招聘主页
- 打开匹配报告
- 打开定制简历
- 备注
- 最近检查时间

链接列显示简短文本而不是原始 URL。数据库同时保存原始链接；若申请链接缺失，则“立即申请”回退到职位详情页。导出前对链接协议进行白名单校验，只允许 `https`、`http` 和经确认的本地文件路径，防止电子表格公式注入。

## 14. 领域 API 与事件

BioJob 后端对 GUI 暴露稳定的领域接口：

- `GET /api/biojob/dashboard`
- `POST /api/biojob/search-runs`
- `GET /api/biojob/search-runs/{id}`
- `POST /api/biojob/search-runs/{id}/cancel`
- `GET /api/biojob/candidates`
- `POST /api/biojob/candidates/{id}/decision`
- `GET /api/biojob/jobs`
- `GET /api/biojob/jobs/{id}`
- `PATCH /api/biojob/jobs/{id}`
- `POST /api/biojob/jobs/{id}/refresh`
- `POST /api/biojob/jobs/{id}/match`
- `POST /api/biojob/jobs/{id}/prepare-application`
- `GET /api/biojob/resumes`
- `POST /api/biojob/exports/xlsx`
- `GET /api/biojob/source-health`

长任务通过 Hermes 现有事件通道发布结构化进度，包括阶段、当前来源、完成数、失败数和可取消标记。GUI 不解析后端日志来判断进度。

## 15. 定时任务与后台运行

默认每天运行一次岗位发现，并每周运行一次链接有效性检查。用户可以修改时间或暂停任务。

Windows 下由 Hermes 后台进程承载任务：

- 用户允许“后台搜索”后，应用注册当前用户级的开机启动或登录后启动。
- 应用窗口关闭不等于终止后台进程；托盘菜单显示运行状态和退出选项。
- 电脑在计划时间关机时，不补跑多次；下次启动只执行一次错过的任务。
- 任务结果进入候选池并发送本地通知，不自动进入正式投递表。
- 数据源连续失败三次后降级并通知用户，不进行无限重试。

## 16. 安全、隐私与合规

1. 默认只监听 `127.0.0.1`，不向局域网或公网暴露 Agent 服务。
2. 本地 API 即使只绑定回环地址也需要随机生成的会话令牌。
3. API Key 和 OAuth Token 使用系统安全存储，不出现在数据库、Excel、错误日志和导出包中。
4. JD、网页内容和搜索结果一律视为不可信输入；其中的指令不得改变系统提示、调用工具或读取本地文件。
5. 岗位解析阶段使用无工具或最小工具模型上下文，防止提示注入。
6. 简历生成只读取已确认的事实和当前岗位，不遍历无关目录。
7. 不保存招聘平台登录 Cookie，不绕过验证码、证书验证或自动化检测。
8. 所有批量状态变更、文件覆盖、数据库恢复和外部提交动作需要用户确认。
9. 自动备份数据库时排除凭据；备份文件采用时间戳并保留最近七个版本。
10. 删除岗位默认采用软删除；清空数据库和永久删除简历必须二次确认。

## 17. 错误处理与恢复

### 17.1 数据源错误

- 网络超时采用有限次数指数退避。
- 401/403 不盲目重试，标记为需要配置或来源限制。
- 429 尊重服务端重试时间并降低并发。
- HTML 结构变化导致解析失败时保存脱敏后的诊断摘要和原始快照位置。
- 单个来源失败不回滚其他来源的成功结果。

### 17.2 模型错误

- Provider 不可用时允许用户选择其他模型后重试。
- 结构化输出不合法时只自动修复一次，之后显示可理解的错误。
- 匹配失败不影响岗位保存，状态标为“待重新分析”。
- 简历生成失败不创建残缺的正式版本，临时文件在任务结束后清理。

### 17.3 数据错误

- 所有状态变更和导入使用事务。
- 启动时检查数据库版本并在迁移前自动备份。
- Excel 导出采用临时文件后原子替换；失败时保留上一版。
- 本地简历链接失效时标记为“文件缺失”，不得静默移除记录。

## 18. 可观测性

本地日志分为应用、数据源、模型、任务和导出五类。日志默认保留 14 天，并进行以下脱敏：

- API Key、Token、Cookie 全量移除
- 简历正文和联系方式不写日志
- JD 只记录岗位 ID、来源和解析阶段，不记录整段内容
- 错误堆栈允许本地查看，但导出诊断包前再次脱敏

首页显示面向用户的健康信息，详细日志只在“诊断”页面查看。

## 19. 测试策略

### 19.1 单元测试

- 公司、岗位、城市和 URL 规范化
- 精确去重、业务键去重和语义候选生成
- 硬规则边界，例如“硕士优先”不得等同于“仅限硕士”
- 投递状态机和非法跳转
- 匹配分数计算及证据完整性
- Excel 公式、超链接和公式注入防护
- 事实主档案可见范围和未确认事实隔离

### 19.2 契约测试

- 每个数据源使用固定响应样本测试，不在普通测试中访问真实网站
- Provider 测试覆盖流式、取消、结构化输出、工具能力和错误映射
- BioJob API 使用 OpenAPI 或等价模式校验请求与响应

### 19.3 集成测试

- 导入简历 → 确认事实 → 搜索岗位 → 确认候选 → 准备投递 → 生成简历 → 导出 Excel
- 多来源发现同一岗位后合并且不丢失链接
- 应用重启后恢复任务、会话和投递状态
- Provider 切换不改变已保存的业务数据
- 数据库迁移失败时自动恢复备份

### 19.4 端到端测试

- Windows 安装、首次启动、升级和卸载
- GUI 列表筛选、批量确认、状态拖动和链接跳转
- 后台任务在窗口关闭后继续运行
- 断网、API 限额、来源失效和磁盘空间不足时的用户提示

### 19.5 事实安全测试

构建一组包含明确缺失经历的测试画像，验证 Agent：

- 不生成不存在的实习和项目
- 不捏造实验数据和量化结果
- 能明确说出岗位差距
- 能抵抗 JD 中要求忽略规则或读取本地文件的恶意指令

## 20. MVP 验收标准

第一版只有同时满足以下条件才算可用：

1. 可在 Windows 安装并作为独立应用启动。
2. 可导入一份 Word 或 PDF 简历并生成待确认事实清单。
3. 至少支持 OpenAI 兼容、Anthropic 和 Gemini 三类 Provider 配置与连接测试。
4. 至少有五个重点企业来源、一个公开发现来源和手动 URL 导入。
5. 自动发现的岗位先进入候选池，未经确认不进入正式表。
6. 同一岗位来自多个来源时能合并，并保留全部可用链接。
7. 每个岗位能生成带证据的匹配分析和明确差距。
8. 状态改为“准备投递”后才允许生成定制简历。
9. 定制简历不能包含个人事实主档案中未确认的经历或数字。
10. Excel 包含投递总表、候选岗位、本周行动和数据字典，并能点击 JD、申请、企业主页、报告和简历链接。
11. 每日搜索可后台执行；失败来源不影响其他来源。
12. 数据、简历和凭据重启后仍可恢复，API Key 不出现在 SQLite 或日志中。
13. 不提供自动投递、自动登录或批量打招呼入口。

## 21. 分阶段交付

由于该产品包含桌面端、Agent 运行时、岗位数据、简历和导出五个子系统，实施必须分阶段，每个阶段独立验收。

### 阶段 0：上游固定与可运行基线

- 固定 Hermes 上游提交和许可证清单
- 在 Windows 上构建并运行原始桌面端
- 建立最小化上游同步策略
- 验证 Provider、Skills、后台任务和打包链路

### 阶段 1：BioJob 数据核心

- SQLite 迁移和领域模型
- 个人事实主档案
- 正式投递状态机
- 基础领域 API 和审计日志

### 阶段 2：岗位发现与候选池

- 数据源插件接口
- 手动 URL、公开发现和首批企业来源
- 规范化、去重、失效检查和候选确认

### 阶段 3：匹配与桌面工作台

- 硬规则和软匹配
- 首页、候选池、岗位详情和投递看板
- Provider 选择和结构化进度

### 阶段 4：简历与 Excel

- 基础简历导入和事实确认
- 定制简历工作流、版本管理和 Word 输出
- Excel 多工作表、超链接和安全导出

### 阶段 5：后台任务与发布质量

- 每日搜索、错过任务补跑和本地通知
- 备份恢复、诊断、安装包和升级测试
- 完整事实安全与提示注入测试

设计文档批准后，实施计划只展开阶段 0，不一次性为全部阶段编写不可执行的超长任务清单。每个阶段完成后根据真实上游代码和测试结果生成下一阶段计划。

## 22. 维护与升级策略

- 配置 `upstream` 指向 Hermes 官方仓库，产品开发使用独立分支。
- 每次同步前运行 Hermes 原始测试和 BioJob 回归测试。
- 上游 Provider 和安全修复优先同步；与求职无关的 UI 新功能可延后。
- 数据库迁移必须向前兼容，并为每次破坏性迁移提供备份和回滚说明。
- 数据源适配器独立版本化；某个来源失效时可以单独禁用或更新。
- 匹配规则和简历提示模板记录版本，旧分析结果不在后台被静默重写。

## 23. 明确延期的功能

以下功能不进入 MVP，但架构不阻止后续增加：

- 本地网页或移动端同步视图
- 面试题生成和模拟面试
- 邮件回执识别和状态自动更新
- 多简历模板市场
- 更复杂的投递效果分析
- OpenCode Runtime 适配器
- 多用户、云同步和端到端加密同步
- 在合规前提下接入更多招聘平台

## 24. 设计完成判定

本设计将 BioJob Agent 定义为“基于 Hermes 的独立、单用户、本地优先求职桌面产品”，并明确了核心流程、系统边界、数据模型、API、错误处理、安全、测试和阶段化交付。后续实现不得把通用 Agent 平台建设、招聘平台自动投递或移动端开发偷偷带入 MVP。

如需变更以下任一基础决策，必须先更新本设计并重新确认：主底座、许可证策略、SQLite 事实源、人工确认边界、简历事实约束或自动投递禁令。
