# BioJob 岗位来源扩充与稳定性改造设计

日期：2026-08-13
状态：待用户书面复核

## 1. 背景与问题

BioJob 0.1.1 默认只有五个启用的企业招聘页和一个关闭的实验搜索源。实际运行时，用户电脑的代理/TUN 将公网域名解析到 `198.18.0.0/15` 基准测试网段；现有 SSRF 校验把这些代理虚拟地址视为非公网地址并拒绝请求，导致多个来源在发出 HTTP 请求前就失败。

即使解决代理兼容问题，许多企业招聘站仍依赖 JavaScript、WAF 或第三方 ATS。用通用 HTML 解析器直接抓企业首页，无法提供稳定、广泛的岗位发现能力。因此本次改造把“岗位发现”和“官方核验”分成两个职责。

## 2. 目标

1. 默认提供足以覆盖生物工程本科秋招主要方向的岗位发现来源。
2. 兼容用户当前使用代理/TUN 的 Windows 网络环境，同时维持 SSRF 防护。
3. 搜索结果保留原始跳转链接、来源名称和核验状态。
4. 同一岗位被多个来源发现时合并，不在候选池重复展示。
5. 让普通用户能理解来源运行结果和下一步操作。

## 3. 非目标

- 不自动登录、抓取或投递 BOSS 直聘、智联招聘、前程无忧等账号页面。
- 不绕过验证码、WAF、登录限制或平台风控。
- 不把搜索摘要视为已经核实的完整 JD。
- 不依赖需要招聘企业授权密钥的 Moka、北森等企业 OpenAPI。
- 不在本阶段实现无人值守自动投递。

## 4. 方案选择

采用“多组公开搜索发现源 + 官方入口核验”的双层模型。

未采用的方案：

- 仅增加企业官网：动态渲染与反爬导致失败率高，覆盖范围仍受限。
- 浏览器自动抓招聘平台：覆盖量高，但需要登录，容易遇到验证码和账号风控，不适合默认启用。

## 5. 来源架构

### 5.1 发现源

新增专用的 `search_feed` 适配器。它读取公开 RSS/Atom 搜索结果，只获取标题、摘要、发布日期和原始链接，不访问搜索结果指向的招聘页面。

默认启用的查询按求职方向和地区拆分，避免一个超长查询降低召回率：

- 生物制药：生产技术、工艺工程、生物工艺
- 质量：QA、QC、GMP、质量管理
- 实验技术：细胞培养、实验员、生物分析、研发助理
- 发酵与微生物：发酵工程、微生物培养、菌株筛选
- 山东：济南、青岛、烟台、济宁、临沂等重点城市
- 周边与大城市：北京、天津、江苏、浙江、上海
- 校园就业网与企业招聘页定向结果

查询应包含“校招、应届生、本科”等限制词，并把明显要求博士、主任、经理、高级职称的结果降权或排除。具体默认查询数量控制在 8–12 个，避免首次运行产生过多低质量噪声。

### 5.2 官方核验入口

企业官方招聘入口作为独立的“核验入口”目录展示。它们提供可点击链接，但不因动态页面无法解析而显示为普通抓取失败。首批覆盖用户画像中重点关注的 CRO/CDMO 和药企，并优先补充山东及周边企业。

核验入口不直接生成虚假岗位记录。只有解析到明确岗位条目，或用户从页面导入岗位后，才进入候选池。

### 5.3 聚合结果标记

每个聚合结果必须保存：

- 搜索来源名称
- 原始结果链接
- 结果域名
- 标题和摘要
- 发现时间
- “待核验”状态

用户打开原链接并补充或确认 JD 后，岗位才能标记为“已核验”。匹配报告和定制简历界面应提醒用户：未核验摘要可能不完整。

## 6. 网络安全与代理兼容

继续禁止回环、链路本地、私网、保留地址、带用户名密码的 URL 和非 HTTP(S) 协议。

对 `198.18.0.0/15` 代理虚拟地址采用有限兼容：

1. 只有内置目录中经过审核、使用 HTTPS 的来源主机可以启用代理虚拟地址模式。
2. 请求前校验 URL 主机必须与来源声明的审核主机一致。
3. 重定向后的主机也必须属于该来源允许的主机集合，否则拒绝。
4. 用户自建来源仍执行原有公网地址检查，不自动放行 `198.18.0.0/15`。
5. 搜索结果链接只作为用户可点击的外部链接保存，不由后端抓取；保存时仍校验协议、控制字符和用户信息。

这样既兼容当前 TUN DNS，也不会把对任意虚拟 IP 的服务器端访问能力开放给用户输入。

## 7. 去重与质量控制

沿用现有 canonical URL 和跨来源归并能力，并补充搜索结果规范化：

- 移除常见跟踪参数；
- 解析搜索引擎跳转链接，尽可能保存目标原链接；
- 同一规范化链接合并来源；
- 没有可靠链接时，以规范化公司、岗位标题和城市作为弱去重键；
- 保留所有来源归因，方便用户判断可信度。

发现结果在进入候选池前执行生物工程岗位相关性过滤。过滤规则必须可测试、可解释，不调用付费模型。完整 JD 的语义匹配仍由现有 AI 匹配功能完成。

## 8. 用户界面

“岗位来源”页面调整为两个区域：

1. **自动发现来源**：显示启用状态、上次运行、发现数量和健康状态，并提供“运行全部启用来源”。
2. **官方核验入口**：按企业展示“打开招聘页”，不使用运行成功/失败语义。

批量运行完成后显示：

- 新增岗位数
- 已合并重复数
- 待核验数
- 成功、部分成功和失败来源数

错误消息转换为中文类别和操作建议，例如：

- 网络代理未兼容
- 域名解析失败
- 网站暂时不可用
- 页面需要浏览器打开核验
- 返回格式已变化

候选岗位卡片展示来源网站、“待核验”标记和“打开原页面”按钮。

## 9. 数据与兼容性

现有用户数据库必须原地升级，不删除来源、候选岗位、个人事实或投递记录。

默认目录更新遵守既有用户修改保护：用户手动关闭、重命名或修改过的来源不会被启动时强制覆盖。旧的动态企业页来源迁移为核验入口时，保留其历史运行记录。

若新增字段，使用可重复执行的 SQLite 迁移，并为旧记录提供安全默认值。

## 10. 错误处理与可观测性

单个来源失败不能中断其他来源。批量运行返回每个来源结果和汇总。

日志保留底层错误用于诊断，界面仅显示去敏后的分类消息。来源健康状态区分：

- 未运行
- 正常
- 部分成功
- 需要浏览器核验
- 失败

## 11. 测试与验收

自动测试至少覆盖：

- 代理虚拟 DNS 仅对审核主机放行；任意用户来源仍被拒绝；
- 重定向不能逃离允许主机集合；
- 搜索 Feed 解析、链接解包、过滤和去重；
- 某个来源失败时批量运行继续；
- 数据库升级保留现有数据和用户来源设置；
- 中文错误类别与批量运行汇总；
- UI 的运行全部、官方入口、待核验标记和原链接跳转；
- 既有候选池、投递表、事实库和简历功能回归。

本机验收标准：

1. 在用户当前代理/TUN 环境中，内置搜索源不会再因 `198.18.x.x` 直接失败。
2. 默认自动发现来源不少于 8 个，覆盖四类岗位方向和山东/周边地区。
3. 一次批量运行不会因单一网站失败而终止。
4. 候选岗位均可看见来源并点击原始链接。
5. 安装升级后原有 BioJob 数据完整保留。

## 12. 发布

完成测试后提升补丁版本，生成 Windows 安装包，在本机覆盖安装并验证启动、来源批量运行、候选链接和数据保留，再更新 GitHub Release。发布说明明确搜索结果需要用户核验，且不会自动投递。
